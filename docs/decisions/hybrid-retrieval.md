# Hybrid 검색

[[embedding-config-surface]]에서 embedding 모델의 출처를 확정하고 백엔드는
미뤄뒀다. 이제 백엔드가 존재하며, 이 문서는 그 형태를 결정한 세 가지 —
문서를 어떻게 쪼개는지, 벡터를 어떻게 캐시하는지, 두 랭킹을 어떻게
결합하는지 — 를 기록한다.

## 시맨틱 쪽은 검색한다, 단순 재정렬이 아니다

떠올리기 쉬운 설계는 BM25가 후보를 뽑고 벡터가 재정렬하게 하는 것이다.
그러나 그 설계는 embedding을 도입할 이유가 되는 바로 그 경우에 무용하다:
쿼리와 단어를 하나도 공유하지 않는 문서는 애초에 BM25 후보가 되지 못하므로,
아무리 재정렬해도 떠오르지 않는다. `revert`로 검색해서는 `rollback`이라고만
적힌 런북에 결코 닿을 수 없다.

그래서 벡터 검색은 위키 전체를 대상으로 돌며 자체 후보를 기여하고, 이
후보들이 융합(fusion) 전에 lexical 후보와 합집합된다.

여기서 두 가지 결과가 따라오며, 둘 다 의도된 것이다:

- **태그 스코핑은 시맨틱 히트에도 적용된다.** 공유 위키 하나를 `project:foo`
  같은 태그로 분할하는데, 벡터 쪽이 우회할 수 있는 필터는 필터가 아니다.
- **`min_score`는 적용되지 않는다.** 그것은 BM25 임계값이고, lexical 쿼리가
  매칭하지 못한 문서에는 BM25 점수 자체가 없다.

## 융합은 점수가 아니라 순위로 한다

BM25 점수와 코사인 유사도는 비교 가능한 값이 아니며, 서로에 맞춰 정규화하면
혼합 결과가 우연히 매칭된 후보 수에 좌우된다. Reciprocal rank fusion은 대신
두 쪽의 *순위*를 결합하므로 그런 결합 의존이 없다.

교과서적 RRF에서 한 가지 조정: 코사인 유사도가 0 이하인 문서는 시맨틱 랭킹의
맨 아래에 두는 대신 랭킹에서 제외한다. 코사인 0은 관계가 *없다*는 증거이고,
그런 문서들끼리 순위를 매기면 가장 덜 무관한 후보가 얻은 적 없는 높은 시맨틱
순위를 물려받게 된다.

## 벡터는 행이 아니라 내용으로 주소를 매긴다

post-commit hook은 커밋마다 재색인하고, 재색인은 모든 chunk 행을 다시 쓴다.
따라서 chunk id를 키로 삼은 캐시는 커밋마다 버려지고 재계산된다 — 정확히
[[embedding-config-surface]]가 진짜 비용으로 지목한 그 재계산이다.

대신 `(chunk 텍스트 해시, model)`을 키로 쓰면 캐시가 재색인을 살아남고, 같은
섹션을 반복하는 두 문서가 벡터 하나를 공유하며, 헤딩 하나를 고치면 chunk
하나만 다시 embed된다. 텍스트가 더 이상 어디에도 없는 벡터는 매 패스 후
정리된다.

## 백엔드는 HTTP이고, core에 포함된다

앞선 결정은 torch와 sentence-transformers가 몇 초짜리 `uv tool install`을
수 기가바이트짜리로 만든다는 이유로 백엔드를 선택적 extra 뒤에 두었다. 그
논리는 *in-process* 백엔드에 대한 것이었다. 사용자가 이미 돌리고 있는 모델
서버로의 HTTP 클라이언트는 표준 라이브러리 외에 아무것도 필요 없으므로
core에 포함된다. 런타임 의존성은 여전히 typer와 rich뿐이다. in-process
백엔드라면 여전히 extra가 필요하다.

로컬 서버들이 실제로 쓰는 방언은 두 가지로 충분하다: Ollama의 `/api/embed`,
그리고 vLLM, llama.cpp, LM Studio, TEI가 노출하는 OpenAI 호환
`/v1/embeddings`. 요청 본문은 동일해서 라우트와 응답 형태만 다르며, 응답은
설정된 방언이 아니라 응답 자체의 형태로 파싱한다.

OpenAI 응답은 사용 전에 각 항목의 `index`로 정렬한다. 스키마는 배열 순서를
보장하지 않으며, 순서가 어긋난 응답은 모든 텍스트를 다른 텍스트의 벡터와
조용히 짝지어 버린다 — 눈에 보이는 증상이 없는 손상이다.

## 스캔은 의도적으로 선형이다

쿼리 하나를 채점한다는 것은 설정된 모델의 모든 벡터를 로드해 Python에서
코사인을 계산한다는 뜻이다. 이 프로젝트가 스스로 잡은 규모 — 문서 1000개
위키에 chunk 약 5000개 — 에서 그것은 밀리초 단위이고, 덕분에 DB는 벡터 색인
확장을 설치할 필요 없는 평범한 SQLite 파일로 남는다. 스캔이 체감되는 위키라면
이미 이 저장소를 벗어난 위키다.

## 여기의 어떤 것도 검색을 깨뜨릴 수 없다

모든 진입점은 예외를 던지는 대신 "unavailable"을 반환한다: 모델 미설정,
엔드포인트 없음, 차단된 원격 호스트, 죽어 있는 서버, 파싱되지 않는 응답,
폭이 다른 벡터 — 전부 BM25로 폴백한다. 모델 서버가 꺼진 위키는 검색이 약간
나빠진 위키일 뿐, 응답을 멈춘 위키가 아니다.

중간에 실패한 embedding 패스는 남은 chunk 수를 보고하고 0으로 종료한다 —
문서는 색인되어 검색 가능하고, 벡터는 다음 실행에서 따라잡는다.
